# Розділ 5. Вирішення проблеми перезавантаження функцій

Ada підтримує перезавантаження підпрограм та операторів [AAR95, розділ 8.3]. Це означає, що використання певного ідентифікатора чи оператора (так званого *дизайнатора*) може позначати кілька сутностей, які водночас є видимими в даній точці програми. Перезавантажені підпрограми повинні відрізнятися принаймні в одному з наступних аспектів: (1) чи є підпрограма процедурою чи функцією; (2) якщо це функція, то типом її результату; (3) кількістю параметрів; (4) типом кожного з параметрів. Ці властивості разом називаються *профілем типів параметрів та результату* підпрограми. Наприклад, у одній точці програми можуть бути видимими такі операції:

```ada
function  Op (x : Integer) return Integer;              -- (Op1)
function  Op (x : Integer; y : Integer) return Integer; -- (Op2)
function  Op (x : Float) return Integer;                -- (Op3)
function  Op (x : Integer) return Float;                -- (Op4)
procedure Op (x : Integer);                             -- (Op5)
```

Слід зазначити, що операції, які відрізняються лише назвами формальних параметрів, але не їхніми типами, не можуть бути доступними в одній точці: або одна з них приховує іншу через правила області видимості, або ж такі оголошення є недопустимими.

Це поняття добре відоме з більшості інших мов програмування; перевантаження в них найчастіше застосовується до операторів. Розв’язання проблеми перевантаження полягає у виборі серед доступних варіантів реалізації (так званих «кандидатських інтерпретацій») саме того варіанту, який відповідає контексту його використання. У найпростішому випадку оператори визначаються за типами своїх операндів: вираз *(A+B)* означає додавання цілих чисел або додавання чисел з плаваючою комою, залежно від типів `A` та `B`. Це ж правило поширюється і на підпрограми: кандидатська інтерпретація залишається в розгляді, якщо типи фактичних аргументів виклику сумісні з формальними параметрами підпрограми.

На відміну від багатьох інших мов програмування, у Ada також використовується контекст виклику для визначення перевантаженого імені [AAR95, Розділ 8.6]. Наприклад, програма може оголошувати кілька функцій, чиї сигнатури відрізняються лише типом повернення значення (випадки (1) та (4) вище). Наслідком використання контексту є те, що перевірку типів виразів та ідентифікацію операторів неможливо виконати під час одного спускового проходу по дереву виразу – на відміну від більшості інших імперативних мов. Замість цього потрібен алгоритм з двома проходами (Algol68 також передбачав подібні правила визначення, тому для нього також був необхідний багатопрохідний алгоритм).

У подальшій частині цього розділу ми описуємо алгоритм вирішення двоетапного типу, який реалізовано у GNAT. Спочатку наводиться загальний опис цього алгоритму; пізніше цей опис доповнюється додатковими деталями та інформацією про структури даних, які використовуються для зберігання варіантів інтерпретації перевантаженого ідентифікатора.

## 5.1 Алгоритм вирішення

Алгоритм визначення розв’язку складається з двох основних кроків:

1. На першому етапі до кожного ідентифікатора прив’язується набір його можливих варіантів інтерпретації; після цього з цього набору відбираються ті варіанти, які відповідають типам їхніх аргументів. Якщо у такому наборі лише один елемент, то ідентифікатор є однозначним.

   Цей процес виконується для кожного *повного контексту* – тобто для такої мовної конструкції, для якої необхідно визначити правильну інтерпретацію без аналізу більшої частини програми. Повними контекстами є: елемент контексту, декларативний елемент чи оголошення, оператор, асоціація аргументів у прагмах, а також вираз у операторі вибору [AAR95, розділ 8.6(4-9)]. Таким чином, виклики процедур та оператори присвоєння є прикладами повних контекстів.

2. На другому етапі до повного контексту застосовується типова інформація для вибору єдиної можливої інтерпретації для кожної його складової. Наприклад, права частина оператора присвоєння може містити виклик функції з перекритою реалізацією; проте якщо тип лівої частини є унікальним, він однозначно визначає, яка саме функція викликається. Після визначення функції її формальні параметри використовуються для визначення типів фактичних аргументів у виклику, і так далі.
Проблему розв’язання перевантажень найкраще пояснити на простому прикладі (детальний опис цієї проблеми, а також формальна специфікація алгоритму наведені у [vK87, розділ 4.5]). Припустимо наявність наступних функцій:

```ada
declare
    function F (A , B : T1) return T  is ...  -- (F1)
    function F (A , B : T2) return T1 is ...  -- (F2)
    function F (A , B : T2) return T2 is ...  -- (F3)
    Var1, Var2, Res : T2;
begin
    Res : = F(Var1 , Var2);
end ;
```

Тип виразу `F(Var1,Var2)` неможливо визначити лише на підставі самого виклику функції; необхідно враховувати контекст, у якому він з’являється. Під час першого проходу аналізу «знизу вгору» на кожному вузлі піддерева виразу обмежується набір можливих операторів шляхом виключення тих, чиї типи формальних параметрів не відповідають типам фактичних аргументів. У цьому прикладі друга та третя версії функції `F` є дійсними кандидатами; тож до виклику `F` прив’язується набір `F2`, `F3`. Під час другого проходу аналізу «зверху вниз» цей набір ще більше скорочується за рахунок виключення будь-яких операторів чи функцій, тип результату яких не відповідає контексту. У нашому прикладі контекст вимагає, щоб тип результату був `T2`; з огляду на це під час другого проходу аналізу залишається лише функція `F` з третього визначення.

### 5.1.1 Додаткові відомості щодо ітерації „знизу вгору“

Під час першого проходження можна також вибирати можливі варіанти інтерпретації на основі співвідношень іменованих параметрів. Розглянемо два оголошення:

```ada
function F (A : Integer; B : Integer := 0) return Integer;  -- (F1)
function F (C : Integer) return Integer;                    -- (F2)
```

Ці дві функції мають різні набори параметрів, проте виклик `F(5)` залишається неоднозначним, незалежно від контексту: він може означати як `F(5,0)`, так і `F(5)`. Однак можна написати `*F(C= 5)*`, щоб усунути цю неоднозначність – адже використання іменованих параметрів вказує на те, що лише `F2` є можливим варіантом інтерпретації.

Процес визначення відповідного варіанту перевантаження ускладнюється специфічними правилами, які діють у різних контекстах, а також для окремих елементів цих контекстів; крім того, існують правила визначення, які стосуються не одного конкретного типу, а цілого класу типів. Наприклад:

1. Межі оголошення цілочисельного типу можуть визначатися будь-яким цілочисельним типом.  
2. Умова у операторі if може бути будь-якого булевого типу.  
3. Операнди оператора порівняння на рівність не повинні мати обмежень.
Слід зазначити, що під час визначення перевантаження вирази самі по собі можуть вважатися перевантаженими — тобто мати кілька можливих типів. Наприклад, обраний компонент може бути перевантаженим, якщо його префікс є перевантаженим.

Під час знизу-вгори проходження піддерево позначається наступним чином:

– Числові літерали позначаються відповідним універсальним типом; символьні літерали позначаються як `Some_Character`, оскільки вони сумісні з будь-яким типом символів чи переліковим типом, який допускає використання символьних літералів.  
– Агрегати, які є літеральним представленням складених значень, позначаються як `Any_Composite`, що вказує на те, що контекст має бути типом запису чи масиву. Зауважимо, що компоненти агрегата не використовуються під час обробки знизу вгору: сам агрегат визначається на основі контексту.  
– Для ідентифікаторів правила видимості визначають можливі варіанти інтерпретації; якщо така інтерпретація допускає перевантаження (тобто йдеться про підпрограму чи літерал переліку), то аналізується весь контекст для пошуку інших можливих варіантів інтерпретації. Перебираються всі елементи ланцюга омонімів, щоб знайти сутності з такою самою назвою, які можуть бути оголошені у зовнішніх областях видимості чи в пакетах у контексті поточної компіляції. Усі вони додаються до структури даних, яка концептуально пов’язана з ідентифікатором та описується нижче (див. розділ 5.1.2).  
– Для кожного виду виразів існують власні правила роздмухування. У семантичному описі мови Ada кожна декларація типу створює певні неявні оператори, які застосовуються до цього типу. Наприклад, кожен нелімітований тип має власний оператор рівності; кожен арифметичний тип – власні арифметичні оператори тощо. Оскільки декларації типів у програмах на Ada зустрічаються дуже часто, видається доцільним знайти компактний чи неявний спосіб опису цих операторів, замість того щоб явно визначати окремі сутності для кожного з них. Це буде детально розглянуто у наступних пунктах.
У GNAT усі заздалегідь визначені оператори оголошуються лише один раз — у внутрішньому представленні пакета Standard. Якщо операнди оператора є перезавантаженими, різні інтерпретації відповідають різним типам; проте сама назва оператора залишається унікальною. Відсутність явних операторів для кожного типу певною мірою ускладнює перевірку типів, але забезпечує значну економію пам’яті та покращення продуктивності. Оператори мають такі характеристики:

1. Типи обох операндів мають бути однаковими.  
2. Контекст не визначає очікуваний тип операндів, адже він лише вказує, що результат має бути типу `Boolean`.
Розглянемо вираз *f(x)=g(y)*, де обидві функції *f* та *g* є перевантаженими, а користувачем не визначено жодних операцій порівняння; тобто доступною є лише стандартна операція рівності. Аналіз знизу вгору дозволяє визначити можливі варіанти інтерпретації кожного виклику функції. Потім шукаються типи, які зустрічаються у обох наборах можливих інтерпретацій – тобто обчислюється перетин множин кандидатських типів для обох операндів. Якщо цей перетин містить більше одного типу, вираз є неоднозначним незалежно від контексту. Якщо ж у перетині лише один тип, то операція рівності має єдину інтерпретацію з булевим типом.

У цьому розділі ми згадали деякі типові правила розв’язання виразів. Додаткові деталі можна знайти у фронтенд-пакетах `Sem_Ch4` та `Sem_Type`.

### 5.1.2 Структури даних

Семантичний аналізатор зберігає інтерпретації ідентифікатора у глобальній таблиці перевантажень. Кожна інтерпретація являє собою пару (ідентифікатор, тип). Вирази також можуть бути перевантаженими, але не мають назви; тому відповідні інтерпретації є парами, у яких просто повторюється тип. Стандартні примітиви для обробки ітераторів – `Get_First_Interp` та `Get_Next_Interp` – систематично використовуються під час аналізу та розв’язання задач, пов’язаних із перевантаженими конструкціями. Поширеним прийомом у обробці типів є перевірка того, чи може певний перевантажений вузол використовуватися у даному контексті. Процедура *Has Compatible Type (T, N)* перебирає всі інтерпретації для `N` та повертає значення `True`, якщо хоча б одна з них має тип `T`. Детальніша інформація міститься у пакеті `Sem_Type`.

### 5.1.3 Додаткові відомості щодо зверху-вниз проходження

Другий етап визначення типів полягає у проходженні по AST від кореня до листків та поширенні інформації про тип, задану контекстом, на кожен підкомпонент цього контексту. Наприклад, якщо взяти наступне:

```ada
declare
   procedure P (X : Float; Y : Integer);    --  P1
   procedure P (X : Float; Y : Float);      --  P2
   function  F (X : Float) return Integer;  --  F1
   function  F (X : Float) return Float;    --  F2
   ...
begin
   P (F (5.0), 2.2);
end ;
```

Під час знизу-вгору аналізу встановлюється, що виклик функції `F` може мати кілька варіантів реалізації: `F1` та `F2`. Аналогічно, ідентифікатор `P` може позначати як `P1`, так і `P2`. Під час аналізу самого виклику обирається варіант `P2`, що, у свою чергу, визначає тип першого фактичного аргументу як `Float`. Ця інформація про тип потім застосовується до виклику `F(5.0)`, у результаті чого обирається саме реалізація `F2`.

Для кожної мовної конструкції у пакеті фронтенду `Sem_Res` існує відповідна підпрограма, яка застосовує інформацію про контекст до складових частин цієї конструкції. Наприклад, розглянемо перевантажений індексований вираз:

```ada
F (G (x)) (H (y))
```

... де `F`, `G` та `H` є перевантаженими викликами функцій. Після визначення типу контексту `CT` ми перебираємо всі можливі варіанти реалізації `F` та залишаємо той, який повертає масив, елементи якого мають тип `CT`. Коли єдина коректна реалізація `F` встановлена, її формальний параметр визначає тип, необхідний для обчислення `G(x)`; тип компонентів результату цієї функції, у свою чергу, використовується для визначення типу `H(y)`.

Мова демонструє синтаксичну неоднозначність, яка вимагає спеціальної обробки. Розгляньмо наступні оголошення:

```ada
type Vector is array (Integer range ) of Integer;
function F (X : Integer := 10) return Vector;
```

Вираз `F(5)` може інтерпретуватися двояко: як виклик функції з параметром *5*, який повертає вектор, тобто `F(X=¿5)`, або як індексування для виклику функції без параметрів, при якому використовується значення за замовчуванням, тобто `F(x=¿10)(5)`. Ці два варіанти інтерпретації відповідають різним структурам AST; правильна інтерпретація визначається контекстом – очікуваним типом результату виклику, яким може бути або `Vector`, або `Integer`. Проте є незручним зберігати для цієї конструкції дві різні структури даних. Тому парсер будує саме перший варіант інтерпретації, а процес розв’язання викликів функцій враховує саме цей випадок (детальніше описано у `Analyze_Call` та `Resolve_Call`).

## 5.2 Підсумок

Розв’язання проблеми перевантаження підпрограм та операторів вимагає використання алгоритму, який складається з двох проходів. Під час першого проходу кожному ідентифікатору приписується множина його можливих інтерпретацій, сумісних із типами аргументів. Якщо ця множина містить лише один елемент, то вибір інтерпретації є однозначним. Під час другого проходу типова інформація застосовується до всього контексту для визначення єдиної інтерпретації для кожного елемента конструкції. Цей аналіз здійснюється для кожного *повного контексту* – тобто для такої частини програми, яку в мові Ada визначено як конструкцію, для якої необхідно виконати розв’язання проблеми перевантаження без розгляду більшої частини програми.
